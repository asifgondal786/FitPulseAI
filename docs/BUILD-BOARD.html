Open work, in the order it matters

Four items

Ranked by what unblocks the most downstream work, not by what the roadmap implies next.

01

Run through the app and write down the gaps Yours

Your pass over frontend and backend functionality now that Phase 4 is closed. This is the input that reorders everything below it.

Why first: a list of real defects from someone using the product beats any list I can generate from the code.
02

Store per-set and per-exercise performance Data model

Sets, reps and load per exercise per session. Nothing records this today, so the Why Button has to decline the master plan's own headline example — "you stalled on bench press three weeks running" — because there is no bench press history to read.

Why it's load-bearing: not a wording fix. It changes the schema, both persistence adapters, the logging route and the Progress view, and every future progression feature waits on it.
03

Give the frontend a test runner Zero today

282 backend tests and no frontend runner configured at all. Every UI defect of the last three increments — the unstyled auth screen, the native Back button, the mis-centred icons, the dark plate — was found by looking at a screenshot, and each would have shipped past a green suite.

Why before more surface: the browser-driving loop keeps paying for itself, which is the tell that it should be automated rather than repeated. The Phase 4 gap pass proved it twice over — neither of the two remaining frontend fixes was reachable from the backend suite.
04

Finish onboarding, and teach memory Urdu Partial

Onboarding asks four of the ten fields the generator reads — goal, environment, equipment, available days. It never asks limitations, session duration, fitness level or dietary preferences, and the profile has no age, height, weight or gender at all. Separately, the memory extractor is English-only while voice already speaks three languages.

Why them together: both are the product knowing less about the person than it claims to. The generator guesses in the gaps, and the two layers disagree about which languages the product supports.

Pulled forward from deferred

New scope

Three of these sit in the master plan's Explicitly deferred list, and one is a fork the plan asked to be settled before implementation that was never taken. Recording them here so they stop being invisible.

A

Camera form analysis, with a camera picker New

Form checking and rep counting from a live camera. The specific requirement you raised: on desktop the app must let a person choose which camera to attach, because a desktop has no built-in one and an external webcam or a second device may be the right lens. That means enumerating input devices, showing them by label, and remembering the choice — mobiles get their built-in camera and never see the picker.

What it needs: getUserMedia plus on-device pose estimation (MediaPipe or TF.js Pose — a real ML dependency, first in this project). Frames stay on the device, which matches how voice already works. A placement question comes with it: the plan's open question is whether this counts as diagnosing a movement fault.
B

Wearables — Google Fit, HealthKit, Garmin New

Read steps, heart rate, sleep and workout sessions rather than asking a person to type them. The churn model in Phase 3 is currently fed by manual logging only, so a rhythm break it could see directly is a rhythm break it currently infers.

What it needs: OAuth against each provider, and a hard platform split — Apple's HealthKit has no web API, so health data on iOS needs a native bridge. This is the item that cannot be done in a browser.
C

Native Android and iOS Architecture fork

The app is responsive web and already works at 430px in a mobile browser, so responsive on all screens is done for the browser. Native apps are a different thing, and the master plan said to settle Flutter-versus-React-Native before implementation began — that fork was never taken, because the build went React web.

The three routes: wrap the existing React app with Capacitor and gain store presence and native bridges cheaply; rewrite in React Native and keep the language but not the code; or ship a PWA and accept no App Store. HealthKit and reliable background reminders are the features that decide it.

Gaps inside the shipped phases

Recorded in the build log

Each phase recorded its own gaps as it shipped. These are the ones still open below Phase 4. Phase 4's own surviving gaps are three platform limits and one deliberate product call — barge-in that trails a turn behind, no on-device Urdu voice, outcome-claim workout names announced generically, and a sub-thirty-second session logging reps but no minutes — each written up with its reasoning in the build log rather than left as an unexplained missing feature.

—

Phase 4's remaining gaps are accepted, not overlooked

None of the four is a fix waiting to be made. Barge-in needs detected speech rather than a sent transcript, which is a permissions and echo-cancellation problem. Urdu TTS depends on whether the platform ships a usable ur-PK voice. The generic announcement for an outcome-claim name is the safety layer correctly refusing to speak a promise. And a 25-second session is left with no duration because rounding it up to "1 minute" would put a figure in someone's history larger than the work they did.

Why recorded: so a later pass can tell a decision from an oversight. The first three are platform limits; the last is a product call that a future change should answer with a seconds field rather than by making minutes lie.
—

The Overview still shows a hardcoded coach note

The "A note for you" panel says "You've been consistent this week…" regardless of the log, and it now sits directly above a card that is derived from real data. The difference is conspicuous in a way it was not before Phase 3.

—

Nothing is ever delivered

Notification preferences have an API, storage and a Settings UI, but no reminder has ever been sent. The Sunday Letter is composed on request rather than arriving — the master plan's letter is something that shows up.

—

Recall is lexical, not semantic

The embedding layer is deterministic and runs offline. A paraphrase with no shared vocabulary misses until a real embedding provider is configured. There is also no memory expiry policy — nothing is forgotten automatically.

—

The churn model is not personalised

Weights are hand-set constants with no per-user calibration. Defensible against one person's history, and the thing to revisit once there is more. The weekday-drift signal also rarely fires alone — it is largely redundant with silence.

Standing constraints

Non-negotiable
These do not change as features land. The service-role key and JWT secret stay in backend environment variables and never reach the React frontend. No LLM or third-party key is exposed client-side. Real health data and session tokens never enter version control. The safety layer always constrains output and never surfaces as a mode a person can switch off. Red-flag screening never depends on the AI service being up. The product does not diagnose, prescribe, or promise a health outcome — including when a workout is named after one, which is why an outcome-claim name is announced with a generic line rather than read aloud.
